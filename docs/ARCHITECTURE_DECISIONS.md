# Architecture Decisions

This document records the major architectural decisions made during the development of NS3 Central.

## 1. Outbound-Only Communication

**Context:** Central needs to monitor devices across many isolated, secure networks (Sites) where inbound firewall rules are strictly prohibited.

**Decision:** The Collector daemon will only initiate outbound HTTPS connections to Central (e.g. `POST /api/v1/collectors/register`). Central will *never* initiate a connection to a Collector.

**Consequences:** 
- Drastically simplifies network deployments (no inbound NAT or firewall holes required).
- Work must be distributed via a "Pull" mechanism instead of a "Push" mechanism.

## 2. Pull-Based Work Distribution & Job Leasing

**Context:** Central is the source of truth for what needs to be monitored, but Collectors execute the work. If Central pushed jobs, it would need to know the real-time load of every Collector, and if a Collector dies, the pushed job is lost.

**Decision:** 
- **Central owns jobs, Collectors lease them.**
- Collectors periodically call `POST /jobs/pull` to request work based on their `available_capacity`.
- Central "leases" the job to the Collector by assigning a `lease_token` and `lease_expires_at`.

**Consequences:**
- **Horizontal Scaling:** Multiple Collectors at the same Site can pull jobs concurrently.
- **Fault Tolerance:** If Collector A dies mid-job, its lease expires, and Central re-queues the job for Collector B.
- **Simplicity:** Collectors do not need to store retry policies or polling schedules.

## 3. Idempotent Job Completion

**Context:** Network interruptions can cause a Collector to successfully complete a job, send the result to Central, but lose the HTTP response. The Collector will retry sending the result.

**Decision:** All state-mutating API endpoints (Start, Complete, Fail) require an `Idempotency-Key` header. Central safely processes the first request and returns the same successful response for subsequent retries without duplicating the result or failing.

## 4. Derived Online Status

**Context:** Tracking whether a device/collector is "online" or "offline" in a distributed system is error-prone if stored as a static boolean field. A crashed daemon cannot update its status to "offline".

**Decision:** We never store `status = online`. Instead, we store `last_heartbeat`. The status is computed at read-time (e.g., `NOW() - last_heartbeat < 180s = ONLINE`). 

## 5. Event Sourcing for Audit Logs

**Context:** Standard logging is insufficient for tracking the lifecycle of Collectors across a distributed fleet.

**Decision:** We write `CollectorEvent` records to the database for every major state transition (REGISTERED, HEARTBEAT, JOB_LEASED, JOB_COMPLETED). Each event is tied to an `X-Correlation-ID` generated by the Collector, providing a full distributed trace.
